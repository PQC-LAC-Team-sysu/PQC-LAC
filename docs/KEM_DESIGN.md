# KEM 重构说明

## 1. 项目完成了什么

原项目以 C 函数、预处理参数和 DLL 导出接口组织 LAC 公钥加密与密钥封装。重构后将四组参数放在同一个 C++20 库中，调用方不需要改宏重新编译。OpenSSL 替代手写 AES 扩展、散列和原随机数入口，多项式与纠错仍由 LAC 代码负责。

这不是把 C 文件改名为 `.cpp`：接口改为带长度的 `std::span`；资源和错误路径受统一管理；密钥序列化明确定义；乘法内核具有通用和 AVX2 两种后端；BCH 改为无可变全局状态；加入可复现的正确性与性能实验工具。

## 2. 从原理到代码

LAC 在模数 `q = 251`、维度 `n = 512/1024` 的负循环多项式环中运算，系数可以用单字节保存。秘密多项式为稀疏的 `+1 / -1 / 0`；实现存储非零位置，乘法转化为移位加减，避免通用整数多项式乘法。

### 密钥生成

1. 取 32 字节随机种子，用 AES-256-CTR 扩展为三段种子。
2. 第一段生成公共多项式 `a`；第二段抽样秘密多项式 `s`；第三段抽样误差 `e`。
3. 计算 `b = a*s + e (mod 251)`。
4. 公钥保存 `seed_a || b`；私钥保存秘密位置、规范化预留区和完整公钥。

### PKE 加密

1. 用确定性加密种子生成临时秘密 `r` 和噪声 `e1, e2`。
2. 计算 `c1 = a*r + e1`。
3. 消息经过 LIGHT 奇偶校验或 BCH 纠错，然后重复编码映射到系数。
4. 计算 `c2 = b*r + e2 + Encode(m)`，保留规定数量的系数并压缩到每系数 4 bit。
5. 输出 `c1 || compressed_c2`。

### PKE 解密与 KEM

解密计算 `c2 - c1*s`，恢复编码比特并纠错。封装使用随机消息作为输入，按规定的散列派生加密种子和共享秘密。解封装重新加密恢复的消息，再逐字节核对密文；不匹配时返回确定性拒绝秘密。

这些步骤分别位于 `Kem::Impl::{expand_a,sample_positions,encode,encrypt,decrypt}` 和 `Kem::{keypair,encapsulate,decapsulate}`。生产公共 API 仅暴露 KEM；直接 PKE 入口只在测试构建中启用。

## 3. 参数与序列化

所有长度单位为字节；`weight` 指 `+1` 和 `-1` 各自的位置数。

| 参数 | n | weight | 公钥 | 私钥 | 密文 | 共享秘密 | 纠错冗余 |
|---|---:|---:|---:|---:|---:|---:|---:|
| LAC_LIGHT | 512 | 64 | 544 | 1056 | 664 | 16 | 3 |
| LAC128 | 512 | 128 | 544 | 1056 | 704 | 16 | 8 |
| LAC192 | 1024 | 128 | 1056 | 2080 | 1352 | 32 | 9 |
| LAC256 | 1024 | 192 | 1056 | 2080 | 1448 | 32 | 21 |

参数名来自所提供代码，不代表本次工作重新验证了相应安全强度。

公钥前 32 字节是公共种子，后 `n` 字节是规范系数 `0..250`。私钥前 `4*weight` 字节按小端 `uint16_t` 保存 `2*weight` 个互不重复的位置，接着补零到偏移 `n`，最后附公钥。前半位置为正，后半为负。解封装校验范围、唯一性、预留区和嵌入公钥；这些是格式检查，不验证 `s` 与 `b` 的完整代数关系。

`c1` 占 `n` 字节。`c2` 沿用旧实现的块布局：完整 64 系数块将 `[j]` 与 `[j+32]` 打包，尾块两两连续打包。不能用一个普通顺序 nibble 打包器替换，否则旧向量会失败。

保留原 PKE 在编码噪声时的无符号字节截断，例如 `250+125` 变成 `119`。这与模 251 的 `124` 有区别。当前选择保留已验证的密文兼容行为；数学编码修订需要另一个算法版本、失效率评估和独立向量。

BCH 实际参数为 `(m,t)=(8,8),(9,8),(9,18)`。LAC256 有 15 个未使用的校验填充 bit，BCH 层遵从原格式忽略它们；KEM 仍通过完整密文重加密核对。

## 4. PQC-LAC-KEM-v1 的精确定义

记 `H = SHA-256`，`Trunc_L` 为取前 `L` 字节，`L` 为消息/共享秘密长度，`||` 为原始字节拼接。

```text
Encapsulate(pk):
    m    <- CSPRNG(L)
    seed  = H(m || pk[0:32])
    ct    = PKE_Encrypt(pk, m, seed)
    ss    = Trunc_L(H(m || ct))

Decapsulate(sk, ct):
    pk    = sk[n:]
    m', decoded = PKE_Decrypt(sk, ct)
    ct'   = PKE_Encrypt(pk, m', H(m' || pk[0:32]))
    good  = Trunc_L(H(m' || ct))
    bad   = Trunc_L(H(H(sk) || ct))
    ss    = masked_select(decoded AND constant_time_equal(ct, ct'), good, bad)
```

若 BCH 无法恢复消息，解码输出清零，仍走后续重加密和两个候选秘密的计算。对尺寸正确、密钥格式正确但内容非法的密文，返回 `Status::Ok` 和拒绝秘密；应用无法从返回码获得密文有效标志。应用应通过后续带认证数据或握手密钥确认检测双方是否建立同一秘密。

旧向量的正常共享秘密是 `Trunc_L(H(m))`，与新版不同。原实现拒绝分支存在不可依赖的数据使用；v1 对该分支给出确定义。v1 保留原确定性加密种子中的 32 字节公共种子绑定，没有宣称提供标准化的 FO 变换或完整 CCA 安全证明。`H(sk)` 是本研究版的拒绝秘密派生方式；若未来改为私钥中存储独立随机 `z`，应改变私钥格式和协议版本。

密文中没有自动版本协商字段。应用协议必须在认证的握手上下文中标识算法版本和参数集，避免新旧双方得到不同秘密后继续传输。

旧向量私钥的预留区包含原实现未初始化内容；测试适配器仅把该区归零后加载。生产 API 不隐式接受这种非规范私钥。原向量头部的 48 字节 seed 也不能复现原 DLL 的密钥随机数，因此测试不声称逐字节重现旧密钥生成。

## 5. 已落实的优化与修复

| 改动 | 目的与边界 |
|---|---|
| EVP cipher/digest 对象和上下文复用 | 减少重复申请和算法查找；每次重新初始化种子/摘要状态并检查返回值 |
| OpenSSL 私用随机数接口 | 随机数失败立即返回、清除输出；允许显式注入平台随机源和测试随机源 |
| 固定大小工作区 | LAC 自有热路径不进行动态分配；OpenSSL 内部仍可能申请内存，不声称全调用零分配 |
| 公共 `a` 缓存 | 同一公钥重复封装/解封装省去重新生成；只缓存公共信息，不缓存秘密或临时随机种子 |
| 稀疏乘法 + AVX2 | 运行时选择 SIMD，只有专门文件用 `-mavx2`；通用路径仍可独立构建 |
| 无符号 16 位正负累加 | 上界 `192*251=48192` 不超过 65535，避免旧有符号累加问题；最后用 32 位做模约简 |
| 精确尾部处理 | 不依赖调用方额外分配或未初始化内存，避免 SIMD 尾块越界 |
| 显式小端加载与存储 | 移除未对齐指针强转、大小端和别名隐患 |
| 只读 BCH 表 + 每次独立暂存区 | 取消可变全局工作内存，允许不同实例并行 |
| 限定参数的 BCH 解码器 | 编译期生成表；有界 Berlekamp–Massey、完整缩短码 Chien 搜索和重编码校验 |
| 参数和格式检查 | 长度、重叠、非法位置、重复位置、非规范公钥在内核访问前拒绝 |
| 确定性隐式拒绝 | 两候选始终派生，使用 `CRYPTO_memcmp` 和掩码选择 |
| 敏感工作区清除 | 正常与失败返回、对象析构都清除；调用方缓冲区仍由调用方管理 |

这组优化同时包含正确性改进，不能把整套新旧性能差异简单归结为“C++ 比 C 快”。性能报告仅比较同一新版实现的通用与 AVX2 后端。

## 6. API 使用约定

- `Kem` 构造可能因参数、不可用后端、OpenSSL 初始化或内存不足抛异常；构造后三个操作用 `Status` 返回。
- 所有 span 都必须表示真实有效内存；要求精确长度和互不重叠，包括解封装的两个输入区。
- 正常对象在失败时清除尺寸正确的输出，不访问尺寸错误的输出。若调用方让输出与输入重叠，清除输出也可能覆盖那部分输入。
- 移动后的空对象返回 `InvalidArgument`，并清除所有传入输出。可以再次移动赋值恢复使用。
- `Status::Ok` 对解封装仅表示操作完成，不是密文真实性声明。
- 同一 `Kem` 对象不可并发调用；不同实例的 OpenSSL 上下文、工作区和缓存互相独立。
- 注入随机源的上下文由调用方持有，生命周期必须覆盖使用；回调是 `noexcept`，返回 false 表示失败。

## 7. 当前不能宣称的结论

常量时间比较和选择并不使整个解封装变成恒定时间：稀疏秘密索引访存、拒绝采样、BCH 查表/解码仍涉及数据依赖行为。本次没有进行汇编级恒定时间审计、缓存/功耗攻击验证或形式化安全证明。

目前没有 Cortex-M、ARM Linux 或真实 IoT 网络的板上结果。通用后端是移植起点；“关闭 AVX2 测试通过”不等于已经实现低内存 MCU 部署。OpenSSL 的依赖体积、每实例工作区、栈峰值、熵源、持久化密钥和网络分片需要按设备评估。

正常回环与有限压力测试也不能证明极低解密失败率。LAC_LIGHT 及其他参数的失败行为必须通过明确的实验量、置信边界和理论分析评价。

## 8. 面向应用与论文的下一步

建议先把当前版本作为可复现的实现基线，围绕一个具体系统问题开展实验：例如 Linux IoT 网关上的握手尾延迟、受限链路分片成本，或多连接时每线程上下文的内存与吞吐权衡。

实验应区分：旧 C 基线、通用 C++、AVX2、冷启动/热上下文、单连接/多连接；使用相同编译器与参数，报告样本量、median/p95、硬件、频率策略、字节开销、内存和失败统计。当前工具给出了正确性和热调用计时起点，还不是论文完整对照组。

应用层可在此基础上增加带版本标识的握手、身份认证、会话密钥派生、带认证数据加密和重放窗口。要做性能消融实验，应逐项开关缓存或上下文复用并验证输出一致，不将多项改动混为一个因素。生产算法选择和论文新颖性仍需独立研究与评估。
